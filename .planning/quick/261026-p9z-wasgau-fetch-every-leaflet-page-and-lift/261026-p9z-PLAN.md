<objective>
Fix the Wasgau false "no_offer" observed live on 2026-10-26 and lift probation.

Bug (verified live 2026-10-26, re-probed by the planner the same day): the current leaflet (id ep1rP1V0, "WASGAU Prospekt ab 26.10.", 28 pages) prints "Coca-Cola1) verschiedene Sorten, Kiste mit je 12 x 1-l-MW-Flaschen ... 1-l-Preis 0.92" at 10.99 EUR, valid 26.-31.10., on PAGE 1. The app shows Wasgau "no_offer" because fetchCandidates only downloads pages whose 1kcloud index text matches COLA_RE, and 1kcloud's index text for page 1 is TRUNCATED (it stops at "... WaHNsINnS" where the PDF has control chars / unknown-font glyphs). The coords XML of page 1 does contain the box; reconstructPage + extractCandidates on it already yield {page 1, box 31, priceCents 1099, pairing clean, litres 12, 2026-10-26..2026-10-31, verdict accept}. Parsing is fine; only page discovery is broken.

Planner live probe (2026-10-26, real seam, sequential): all 28 pages fetched in ~2.6 s total (page XML 0.16-2.1 MB each, ~12 MB total, largest p14 = 2,078,606 chars < MAX_BODY_CHARS 5,000,000). Candidates across ALL pages: exactly 3 (p1 box 31 accept 10.99 12 l; p20 box 6 reject Bacardi & Coca Cola 0.33 can; p21 box 13 reject 6 x 0.33 PET), colaPages [1, 20, 21]. So the existing candidates .max(50) cap has ample headroom.

User decisions (locked, from the orchestrator):
1. Discovery: fetch the coords XML of EVERY page listed in the index (not just index pages mentioning Cola). Keep strictly sequential one-at-a-time requests, the shared WASGAU_DEADLINE_MS (evaluate; raise with a comment if needed), the leaflet-id cache (only a new leaflet id triggers the full fetch), and all URL/SSRF validation (coordsUrl). colaPages becomes the pages that actually yielded Cola candidates; revisit its .max(8) cap and the candidates .max(50) cap. Replace the index-text "implausible" guard with a sane page-count cap (60) that throws as a bad parse. Remove the now-unused index-text Cola page picker. Update the header comments that say "Cola pages only" (D-09/SC4) to state the new rule and WHY.
2. Set WASGAU_CONFIG.probation = false (the accept candidate was checked against the leaflet image: 10.99 EUR, 12 x 1 l, 26.-31.10.).
3. Update tests for all-pages discovery; add a regression test where a page's INDEX text lacks "Coca-Cola" but its coords XML has the 12x1 l box and it must be found; adjust tests that relied on probation defaulting to true.
4. Do NOT edit data/*.json (CI regenerates them). The committed data/wasgau-candidates.json caches leafletId ep1rP1V0 built by the OLD rule (colaPages [20, 21], no page 1), so the cache must be invalidated for docs produced by the old rule.

Design choices (planner discretion, stated for the record):
- Cache invalidation: add a required `version` field (z.literal(CANDIDATES_DOC_VERSION), value 2) as the FIRST key of the .strict() candidates doc. Old docs lack it, readCandidates already treats any schema failure as a cache miss, so the next run does the full fetch and rewrites the file with version 2. Simplest robust option: no extra request, no comparison logic, and the next rule change only bumps the constant. Rejected alternatives: re-fetching the index every run to compare titles (one more request per run, and the locked id-only cache stays), or a pages-scanned count (informative but not a general "rule changed" signal).
- Page cap: MAX_LEAFLET_PAGES = 60 (observed 26 and 28 pages; ~2x headroom; coordsUrl's own 1..200 range stays the SSRF guard).
- colaPages cap: raised from .max(8) to .max(MAX_LEAFLET_PAGES) because colaPages is now a subset of the fetched pages; candidates .max(50) stays and becomes the documented implausibility guard (a violation throws in buildCandidatesDoc -> Wasgau "error", old cache kept).
- Deadline: 60 s would likely fit (~30 requests, 2.6 s measured from Germany), but per-run requests grew ~15x and every retry costs up to a 10 s attempt timeout plus backoff; raise WASGAU_DEADLINE_MS to 120_000 so a slow-but-healthy runner network does not fail the leaflet. Job has no tight timeout, so the cost is nil.
- Phase 5 SC4 said "stop early where possible"; user decision 1 supersedes that for discovery (good-citizen properties kept: sequential, UA, retry cap, deadline, id cache = once per new leaflet).

Noted, NOT in scope (do not change): 1kcloud reuses leaflet ids (ep1rP1V0 served "ab 12.10." and again "ab 26.10.", with ep16264f89869cea for "ab 19.10." in between). The locked id-only cache is still correct while consecutive weeks get different ids; the planner reports this to the orchestrator separately.

Purpose: Core value — when the 12x1 l case is on sale at Wasgau the app shows it, with price and dates.
Output: All-pages discovery with a version-gated cache, raised deadline, probation lifted, updated + new tests. Code is committed locally only; pushing (which triggers the CI scrape that rewrites data/*.json) is the user's call.
